# 从歌单到一个世界

## 核心判断

选题要求生活碎片产生新的联系，而不仅是换一个容器保存列表。本作品围绕三种关系组织音乐：同艺人的聚合、同歌不同版本的双岛、跨最后播放年份的艺人大桥。用户写入的记忆成为第四种、由本人解释的联系。

用户原始方案采用六片三维大陆，UI 方向采用深色二维城市。经用户选择，最终把两者融合成两个可以切换的同一世界，而不是两个独立应用。二维地图便于观察与投影演示，三维群岛提供地形与空间体验。

## 数据映射

| 字段 | 映射 | 取舍 |
| --- | --- | --- |
| `last_played` 年份 | 时间章节，按时间弧排列 | 是记录切片，不能作为完整历史重播 |
| `artist` | 章节内艺人群组 | 确定性螺旋布局，保持重复生成一致 |
| `genre` | 颜色与地形 | 艺术表达，不是音频情绪分析 |
| `play_count` | 光点 / 岛屿半径与高度 | 平方根压缩极端差异，保留最小可见尺寸 |
| 距参考日年数 | 亮度、静默状态 | 默认采用数据截止日，可切换今天 |
| 标题中的 `Live` / 现场 | 同艺人、规范化歌名匹配 | 名称级匹配，未声称进行音频指纹确认 |

二维半径 `2.4 + 5.2 × sqrt(play_count / max_play_count)`，三维半径 `0.105 × (2.2 + 6.7 × sqrt(play_count / max_play_count))`。为保留可点击性，最低次数的歌也有可见尺寸。三维岛屿底部高度使用 `0.3 + 0.65 × sqrt(play_count / max_play_count)`，顶部按流派改变形状。

同章节中 Live 岛会放在匹配的录音室岛旁边，并有可开关的连线。不同章节的相同艺人形成跨海连接。其他距离来源于数据布局与分组，不声称是音频嵌入的真实风格相似度。

## 原方案的优化

1. 修正“六年六种人格”“彻底离开”“最大岛死亡”等无法被字段证明的断言；改为最后播放年份切片、静默与旧日收藏。
2. 修正 47 对 Live 的估算，实际匹配得到 97 对。所有发现均实时计算，导入新数据后会更新。
3. 时间参考采用最新数据日 2024-12-16；不把 2024 的记录在 2026 年误称为今天仍活跃。
4. 补上记忆笔记、收藏、可迁移备份，让使用者能自己解释音乐与生活之间的关系。
5. CSV 没有音源、valence、energy、首次播放、年度播放或夜间播放字段，因此不伪造音频播放或情绪分析。

## 技术取舍

- React 管理选择、导入、笔记与导航状态；两种渲染器共用纯数据引擎。
- PixiJS 只承担地图绘制；拖动、滚轮与双指缩放用画布指针事件实现。图层静态生成，镜头与地标光环按帧更新。
- Three.js 按章节实例化岛底和岛顶，减少 500 座岛的绘制调用；射线的实例编号直接映射到歌曲。
- 三维模块按需加载，原数据内置；本地生产服务与静态托管均可运行。
- 浏览器 `localStorage` 保存笔记与歌单；写入失败时提示导出，JSON 提供显式备份路径。没有注册、账户或遥测。
- 默认向导是规则检索。在线向导是可选的服务端 HTTPS 模型调用，密钥留在服务端，导航目标通过已有 ID / 艺人 / 年份约束。

## 能力边界

这是对用户提供的音乐元数据的空间表达，不能从中判断人格或心理状态。默认歌单来源真实性未核验。导入格式最多 5,000 条；三维视图需要支持 WebGL 的浏览器。本地音频不会持久上传，换会话后需重新关联。真实大模型调用需要用户配置 API，且受模型服务计费与可用性约束。
